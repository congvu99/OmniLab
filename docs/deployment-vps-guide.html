Deploy OmniLab lên VPS

Site tĩnh Astro và máy chủ đồng bộ tài khoản (sidecar) chạy trên VPS đang có BookSnap + LingoBrain, dùng chung Caddy. Bắt đầu khi code đã push lên GitHub. Nội dung bài học nằm trong git, build thẳng vào image. Máy chủ đồng bộ giữ một DB SQLite nhỏ (tài khoản và tiến độ đã đồng bộ), nên phải bật backup ở chương 6. Làm lần lượt chương 2 → 4, rồi chương 6. Khoảng 20–30 phút, chưa tính build lần đầu.

Thông số của bạn

Điền vào đây, các lệnh bên dưới tự cập nhật (tô vàng). Chỉ lưu trong trình duyệt này.

Nhãn trên mỗi khối lệnh WINDOWS máy tính của bạn · SERVER phiên ssh vps, user deploy · FILE nội dung một file. Mỗi khối lệnh: bấm Copy, dán nguyên khối.
Điều kiện trước Đã làm xong chương 1–5 của hướng dẫn VPS BookSnap: ssh vps, Docker, DuckDNS, Caddy dùng chung + mạng web, /srv/apps thuộc user deploy.

  • ls in đủ Caddyfile compose.yml Dockerfile + deploy.sh. Báo No such file = chưa push hoặc dán thiếu dòng git clone.
  • SITE_URL: tên miền thật của site, dùng lúc build để sitemap.xml đúng domain. Không phải bí mật, chỉ cần đúng. Đổi tên miền sau này → sửa file này rồi build lại (chương 6).
  • SESSION_SECRET: khoá ký cookie đăng nhập. openssl rand -base64 48 cho 64 ký tự; deploy.sh bắt buộc ≥ 32. Đừng đổi khi đã có người dùng: mọi phiên đăng nhập hết hiệu lực. Chạy lại khối này sẽ ghi đè .env, nên chỉ chạy một lần.
  • grep -c phải in 1. chmod 600: chỉ user deploy đọc được. .env không vào git và không vào image.
  • Thư mục dữ liệu là volume của sync, chứa omnilab.db và backups/. Chủ sở hữu phải là uid 1000 (user node trong container). ls -ld phải in drwx------ … 1000 1000. Mode 700 nghĩa là mọi lệnh đụng file ở đây cần sudo. Muốn đặt chỗ khác: thêm OMNILAB_DATA_DIR=/duong/dan vào .env.
  • Bản nghe (tuỳ chọn): GEMINI_API_KEY, thư mục audio riêng và các biến TTS_* cấu hình ở chương 8. Không có chúng, deploy vẫn chạy: tts chỉ dọn dẹp và ngủ, trình phát ẩn. Nên tạo thư mục audio trước lần deploy.sh đầu có tts.

3Build & chạy

Server
cd /srv/apps/omnilab
bash deploy/deploy.sh
docker compose ps
docker compose logs --tail 20 app
docker compose logs --tail 5 sync
  • Lần đầu vài phút: tải Node, cài thư viện, sharp xử lý ảnh, build site (khoảng 73 trang HTML). Image sync chỉ cài Node, không có npm package. Các lần sau nhanh hơn nhờ cache. Log build có sitemap-index.xml created.
  • Kết thúc bằng deploy ok: <commit>. ps: app và sync đều Up … (healthy). tts chỉ Up (không có healthcheck vì không phục vụ cổng nào; trạng thái xem ở log, chương 8).
  • WARN: tts build failed, keeping previous tts container (hoặc tts start failed): site vẫn deploy bình thường, chỉ bản nghe chưa cập nhật. Xem log build rồi sửa, chạy lại; không cần làm gì gấp.
  • Log sync có "message":"sync listening on 0.0.0.0:3000". Mỗi request là một dòng JSON, không có body, mật khẩu hay cookie.
  • Lần deploy đầu có sync, log có thể in deploy.sh đã cập nhật, chạy lại bản mới. Script tự chạy lại một lần, đây là bình thường.
  • Trước lần deploy đầu có sync, lưu header trang tĩnh để so sánh: curl -sI -H 'Accept-Encoding: gzip' https://./ | grep -vi '^date\|^etag\|^last-mod' > base-home.txt (làm tương tự với một bài học và một file /_astro/*.css). Sau deploy chạy lại và diff phải trống: header trang tĩnh không được đổi.
  • Log app là JSON của Caddy ("msg":"serving initial configuration"). Không thấy lỗi error là được.
  • Build dừng ở FIDELITY VIOLATION: nội dung bài học lệch với content-sources/ → sửa trên Windows (pnpm build báo cùng lỗi), push, chạy lại.

Thử sập máy chủ đồng bộ

Nên làm một lần để chắc site vẫn sống khi sync hỏng.

Server

curl -si https://./api/me | head -1

  • Lệnh 2 in HTTP/2 503 (dòng đầu của lệnh 1). Body là {"code":"unavailable"}, không cache. Lệnh 3 in 200: site vẫn chạy.

  • Tab Tôi, mục Tài khoản: đăng ký một tài khoản thử, đánh dấu một bài xong, tải lại trang: tiến độ vẫn còn.
  • Trình duyệt khác (hoặc cửa sổ ẩn danh), đăng nhập cùng tài khoản: thấy bài đã xong.
  • Trang Tìm kiếm gõ 1 từ → có kết quả (đọc search-index.json).
  • iPhone Safari: Thêm vào màn hình chính → mở được như app.

5Chuyển từ Nhân Hòa (Vibe Deploy)

Sao lưu DB đồng bộ (bắt buộc)

Script deploy/backup-sync-db.sh chạy trong container sync: chụp snapshot nhất quán (VACUUM INTO) vào /srv/data/omnilab/backups/omnilab-YYYY-MM-DD.db, giữ 14 ngày. Container chạy cùng uid với DB nên không lỗi quyền.

Server
cd /srv/apps/omnilab
bash deploy/backup-sync-db.sh
sudo ls -l /srv/data/omnilab/backups
  • Kết quả: backup ok /data/backups/omnilab-YYYY-MM-DD.db. Đường dẫn /data là trong container; trên host là /srv/data/omnilab/backups/.
  • Chạy hai lần trong một ngày vẫn chỉ có một file: bản trong ngày bị ghi đè. Ghi qua file tạm rồi đổi tên nên lỗi giữa chừng không làm mất bản đã có.
  • File cũ hơn 14 ngày bị xoá. File khác trong thư mục không bị đụng tới.
  • Bản sao vẫn nằm trên cùng ổ đĩa VPS. Để có bản ngoài VPS, xem phần rclone bên dưới.

Chạy tự động mỗi đêm (cron)

Server
15 3 * * * cd /srv/apps/omnilab && bash deploy/backup-sync-db.sh >> $HOME/omnilab-backup.log 2>&1
  • Thêm dòng trên bằng crontab -e của user deploy. 15 3 * * * theo giờ của VPS: xem bằng timedatectl. Tên file theo ngày Việt Nam, nên lệch múi giờ không đổi tên file.
  • Log ở $HOME/omnilab-backup.log. Hôm sau kiểm: tail -n 3 ~/omnilab-backup.log phải có backup ok.
  • Cron chạy bằng user deploy, nên user này phải thuộc nhóm docker (xem chương 7). Nếu sync đang dừng, lỗi ghi vào log; cần tự docker compose start sync.

Ra ngoài VPS (rclone, khuyến nghị)

Mất ổ đĩa VPS là mất cả bản backup. Đẩy bản sao sang kho khác (Backblaze B2, Google Drive, S3...) bằng rclone. Phần này chưa thử trên VPS.

Server
sudo rclone config
sudo rclone copy /srv/data/omnilab/backups <remote>:omnilab-backups
  • <remote> là tên đặt trong rclone config. Lệnh chạy bằng sudo vì thư mục mode 700 thuộc uid 1000.
  • Đưa vào cron của root (sudo crontab -e), chạy sau lệnh backup, ví dụ: 30 3 * * * rclone copy /srv/data/omnilab/backups <remote>:omnilab-backups.
  • Kiểm sau lần chạy đầu: sudo rclone ls <remote>:omnilab-backups.

Đặt lại mật khẩu, thu hồi phiên

Không có email nên không có quên mật khẩu tự động. Quản trị đặt lại bằng lệnh sau. Lệnh cũng tăng session_version, nên mọi thiết bị đang đăng nhập bị đăng xuất.

8Bản nghe bài học (tts)

Service tts đọc tts-scripts.json (sinh lúc build), gọi Gemini TTS để đọc từng bài, nén thành .m4a và ghi vào thư mục audio. app phục vụ file đó ở /audio/*. Luồng và lý do thiết kế: system-architecture.md, mục "Bản nghe bài học". Đây là phần tuỳ chọn: thiếu GEMINI_API_KEY thì site chạy bình thường và trình phát ẩn.

Hạn mức free tier quyết định tốc độĐợt tạo đầu khoảng 450–500 request cho toàn bộ bài. Ở 10–20 request/ngày (hạn mức free tier của model TTS, xem AI Studio) là khoảng 23–50 ngày; bài nào xong thì bài đó hiện trình phát, không cần làm gì thêm. Bài mới deploy hoặc bài vừa sửa được worker tự nhận ra ở vòng quét kế tiếp.

Google có thể dùng nội dung gửi lênGemini API free tier cho phép Google dùng nội dung gửi lên để cải thiện sản phẩm. Vì vậy chỉ gửi bài học công khai (đúng với nội dung OmniLab). Với người dùng ở EEA, Anh, Thuỵ Sĩ, điều khoản free tier có vùng xám; chủ dự án đã chấp nhận việc này vào ngày 2026-10-28. Không đặt GEMINI_API_KEY thì không có gì được gửi đi (trình phát ẩn).
